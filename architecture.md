# PlannerCapture Architecture

## High-Level Architecture

PlannerCapture is a native macOS client monolith (single process) that delegates task/group persistence to an external local HTTP service (Daily Helper Hub gateway).

Architecture style:
- Client app: Swift monolith (`Sources/*.swift`), no internal microservices/modules.
- External dependency: hub gateway API (`http://127.0.0.1:8765` by default).

## Startup and Module Interaction

### App startup path
1. `@main` in [`Sources/PlannerCaptureApp.swift`](./Sources/PlannerCaptureApp.swift) installs `AppDelegate`.
2. `applicationDidFinishLaunching` initializes:
   - `SettingsStore.shared`
   - `PlannerLogger`
   - notification permissions
   - `MenuBarManager`
   - `FloatingWindowController`
3. Global hotkey is registered via `GlobalHotkey.shared.register(keyCode: 49, modifiers: [.command, .shift])`.
4. Hotkey toggles floating capture panel visibility.

### Window and surface ownership
- Menubar popover: `MenuBarManager` (`MenuContentView`).
- Main planner window: singleton `PlannerWindowController.shared`.
- Settings window: singleton `SettingsWindowController.shared`.
- Floating capture panel: `FloatingWindowController` and `FloatingPanel`.

## Data Flow

### 1) Capture flow
1. User presses `Cmd+Shift+Space`.
2. `GlobalHotkey` callback opens `FloatingWindowController`.
3. Input parsed by `parseCaptureInput(_:)` in [`Sources/CaptureParser.swift`](./Sources/CaptureParser.swift) (extracts status, priority, group, and **due dates** via relative/natural language logic).
4. Parsed payload forwarded to `TaskStore.shared.addTask(...)` including `dueAt` metadata.
5. `TaskStore` calls `GatewayClient.createTask(...)`.
6. On success, `TaskStore` updates local task list/sections and optionally mirrors to CLI (`CLIWrapper`) when `mirrorCLI` is enabled.

### 2) Polling/sync flow
1. `TaskStore` schedules timer in `schedulePolling()`.
2. Poll timer calls `pollForChanges()`.
3. `GatewayClient.fetchLatestSeq()` checks sequence.
4. If sequence advanced, `loadTasks()` fetches groups + tasks.
5. `buildSections(from:)` recalculates section/group presentation model.
6. UI surfaces (`MenuContentView`, planner views) react via `@ObservedObject` updates.

Backoff behavior:
- Poll interval increases exponentially with jitter on consecutive failures (`pollIntervalWithBackoff`).
- Recovery resets failure count and polling cadence.

### 3) Task edit/save flow
1. Task selected in planner list (`PlannerModernView`).
2. `TaskEditDraft` is created from selected task.
3. Save action uses `TaskEditDraft.patchFields()`.
4. `TaskStore.saveTaskEdits` issues `GatewayClient.patchTask`.
5. On success, local task is replaced and sections rebuilt.

## Core Patterns

- State container pattern: `TaskStore` and `SettingsStore` are shared observable singletons.
- Thin view, heavy store: views dispatch to stores/clients; most business logic sits in `TaskStore` and parsing helpers.
- Gateway abstraction: all HTTP requests run through `GatewayClient`.
- Derived view model pattern: `sections` are computed from raw `tasks` using settings-driven logic.

## Sectioning, Sorting, and Grouping Model

Implemented in `TaskStore.buildSections` and `sortTasks` in [`Sources/Models.swift`](./Sources/Models.swift):
- Buckets: `Immediate`, `This Week`, `Other`, `Waiting`, `Done`.
- Inputs considered:
  - task status (`inbox`, `todo`, `in_progress`, `blocked`, `done`, `archived`)
  - due date (`due_at`)
  - starred/priority override (`immediateOverrideEnabled`)
  - group modes (`bucket`, `group_then_bucket`, `bucket_then_group`)
  - visibility settings (`showDoneSection`, `showWaitingSection`, `visibleGroupIds`)

## Error Handling and Recovery Strategy

### Gateway-level errors
`GatewayError` cases:
- `invalidURL`
- `transport`
- `timeout`
- `http(status, body, requestId)`
- `decode`

Error mapping:
- User-facing messages via `GatewayError.userMessage`.
- Detailed diagnostics logged via `PlannerLogger` including request IDs and payload snippets.

### Stale task recovery
- In action handlers, HTTP 404 is treated as stale local state.
- `handleActionError` removes task from local cache and forces `refreshNow()`.

### Optimistic UI behavior
- Star toggle updates UI immediately and rolls back on API failure (`toggleStar`).

## Authentication and Authorization

- Optional bearer token read from `settings.apiToken`.
- Added to requests as `Authorization: Bearer <token>` when non-empty.
- Request correlation header `X-Request-Id` generated per request.

## File Placement Conventions for New Code

- New domain models/API DTO/store behavior: add to [`Sources/Models.swift`](./Sources/Models.swift) unless splitting into dedicated files as part of refactor.
- New planner window UX flows: [`Sources/PlannerWindowController.swift`](./Sources/PlannerWindowController.swift).
- New settings schema/persistence/validation: [`Sources/SettingsStore.swift`](./Sources/SettingsStore.swift).
- New settings controls UI: [`Sources/SettingsWindowController.swift`](./Sources/SettingsWindowController.swift).
- New menubar interactions: [`Sources/MenuBarManager.swift`](./Sources/MenuBarManager.swift).
- Shared reusable SwiftUI visuals: [`Sources/UIPrimitives.swift`](./Sources/UIPrimitives.swift).
- Logging extensions: [`Sources/PlannerLogger.swift`](./Sources/PlannerLogger.swift).

## Known Architectural Risks

- `Sources/Models.swift` is large and combines models, networking, and state management.
- No local offline cache beyond in-memory store.
- No automated contract tests against gateway API.
